# Vibe — Database Architecture

## Overview

Vibe uses **Supabase PostgreSQL** as its primary database. All application data lives in Supabase, not Telegram's internal database.

The database is organized into **modules**, each representing a domain within the application.

---

## Module: Identity

**Purpose:** User accounts, authentication, and session management.

Future tables:

- `users` — Core user data, linked to Telegram user ID
- `sessions` — Authentication sessions
- `auth_providers` — Linked auth providers (Telegram, etc.)

Key considerations:

- User ID is a UUID generated by the application, not the Telegram ID
- Telegram user ID is stored in a separate column (uniquely indexed)
- Never expose internal user IDs to unauthorized users

---

## Module: Profiles

**Purpose:** User profiles, photos, bio, and dating preferences.

Future tables:

- `profiles` — Bio, display name, age, location, etc.
- `profile_photos` — Photos on the user's profile
- `dating_preferences` — Gender preference, age range, distance, goals

---

## Module: Social

**Purpose:** Social feed, posts, interactions.

Future tables:

- `posts` — Text/image/video posts
- `post_likes` — Likes on posts
- `post_comments` — Comments on posts
- `follows` — User follow relationships
- `stories` — Ephemeral story content

---

## Module: Dating

**Purpose:** Discovery, swiping, and matching.

Future tables:

- `swipes` — User swipe actions (like/pass)
- `matches` — Mutual match records
- `super_likes` — Premium super-like actions

---

## Module: Messaging

**Purpose:** Real-time chat between matched users.

Future tables:

- `conversations` — Chat conversation metadata
- `messages` — Individual messages
- `message_reads` — Read receipts
- `conversation_participants` — User participation in conversations

---

## Module: Media

**Purpose:** User-uploaded media and Telegram file references.

Future tables:

- `media` — Media file metadata, storage references
- `media_variants` — Thumbnails, compressed versions

---

## Module: Communities

**Purpose:** Groups and interest-based communities.

Future tables:

- `communities` — Community/group metadata
- `community_members` — Membership records
- `community_posts` — Posts within communities

---

## Module: Payments

**Purpose:** Telegram Stars and digital goods.

Future tables:

- `transactions` — Payment/Stars transaction records
- `virtual_goods` — Available virtual goods (boosts, super likes, gifts)

---

## Module: Subscriptions

**Purpose:** Premium subscription management.

Future tables:

- `subscriptions` — Active/past subscriptions
- `subscription_tiers` — Available subscription plans

---

## Module: Moderation

**Purpose:** User reports, blocking, and content moderation.

Future tables:

- `reports` — User/content reports
- `blocks` — Blocked user relationships
- `banned_users` — Banned accounts

---

## Module: Notifications

**Purpose:** Push and in-app notification management.

Future tables:

- `notifications` — Notification records
- `notification_settings` — User notification preferences

---

## Module: Referrals

**Purpose:** Referral/affiliate tracking.

Future tables:

- `referral_codes` — User referral codes
- `referral_redemptions` — Referral reward events

---

## Module: Analytics

**Purpose:** User behavior and growth analytics.

Future tables:

- `events` — User action events
- `daily_metrics` — Aggregated daily statistics

---

## Module: Admin

**Purpose:** System administration and configuration.

Future tables:

- `admin_users` — Admin user records
- `system_config` — Application configuration key-value store
- `feature_flags` — Feature toggle management

---

## Key Database Principles

1. **Row Level Security (RLS):** All tables must have RLS enabled
2. **User ownership:** Users can only modify resources they own
3. **Soft deletes:** Prefer soft deletes over hard deletes where appropriate
4. **Timestamps:** All tables should have `created_at` and `updated_at` columns
5. **Indexing:** All foreign keys and frequently queried columns must be indexed
6. **Migrations:** All schema changes must be managed through migrations
